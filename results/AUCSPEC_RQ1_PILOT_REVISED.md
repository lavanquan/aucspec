# AUCspec RQ1 minimal pilot — revised plan (C1)

**Status: plan only. Nothing is submitted.** This supersedes `AUCSPEC_RQ1_MINIMAL_PILOT_PLAN.md` (C0) where they differ. Runtime H is
unchanged; the pilot is independent of calibrated verifier pricing (`verifier_price_mode: zero`, no server price, no learning, no
policy search).

## 1. Question and estimand
RQ1: *can aggregate goodput hide a fall in per-client capacity?* The pilot measures, for one fixed policy on the corrected runtime and
a **fixed homogeneous population**, how the per-client useful-token rate floor `x_min(N)` and the aggregate goodput `Y(N)` move
with the concurrency `N`. The estimand is the *controller-achieved, descriptive* curve of this one policy at 18 (N, run-seed) points.
It is **not** a certified `N*(x)`, not an existential capacity, and says nothing about Capacity-DPP or any baseline.

## 4. Workload supply (does a client run out before the window ends?)

`max_new_tokens = 96` is a *cap*. Evidence on this prompt set: 88 of 88 observed samples (40 at cap 96, 48 at cap 48) ended at the
cap, none by EOS (rule-of-three bound: P(EOS before cap) ≤ 3.4 % per sample, 95 %) — so 96 is the working value but **not** a
guarantee. The pilot therefore does not rely on it:

* Hard per-client rate bound: tokens/round ≤ γ+1 = 3 and `T_cycle ≥ 10 + 2·22.2 + 50 + 150 + 78.5 ms = 0.333 s` ⇒ `x_max ≤ 9.0 tok/s`
  (observed single-client rate: 8.97 tok/s). Tokens needed to outlast `T_stop = 160 s` with a 10 % margin: **1,586 per client**.
* Questions needed by mean answer length L: 17 (L=96), 25 (64), 34 (48), 50 (32), 67 (24). **Chosen: 64 per client**, which tolerates a
  mean answer length down to **24.8 tokens**.
* Preflight (CPU, before submission): `scripts/c1/rq1_workload_and_cost_budget.py` and the config test check prompts available
  (1,024 ≤ 1,319) and the table above.
* Runtime guard: the lifecycle assessment is applied to every run; **any exhausted client ⇒ the point is INVALID** (never
  infeasible), the job stops and the point is re-planned with a larger supply. Early-stopped clients are ACTIVE by definition.
* Residual risk (B8): an unusually short-answer subset could still exhaust a client; it is detected, not prevented.

## 5. Virtual versus physical execution cost

| Quantity | Virtual or physical | Pilot setting |
|---|---|---|
| verifier service | **physical** measured batch wall time occupies the single virtual verifier | unchanged (`batch_wall`) |
| draft time | measured on shared GPUs (inflated by contention) **or** isolated profile | `isolated_profile` (needs approval; measured value still logged) |
| RTT, upload, download, 150 ms batch wait | **virtual** (never slept) | RTT 50 ms, payload ≈ 100 B |
| causality waits | **real** time (clients wait for the verifier horizon) | cost factor 1–3 in the budget |
| run length | ≈ virtual length × r(N), r = real s per virtual s | measured r = 0.54 (N=1), 1.00 (N=8); assumed 0.8/0.9/1.3/1.6 for N = 2/4/12/16, ×(1–3) for causal waiting |
| startup | physical, per process | 130 s (job 51097012: 360 s elapsed, 230 s run) + 20 s teardown |

## 6. What is measured and the pre-registered decision rules

Per run (`scripts/c1/analyze_rq1_pilot.py`, unit-tested on synthetic pilots): per-client rates over the exact window (absent = 0),
`x_min`, mean, `Y = Σ x_i`, `N·x_min`, Jain index, `x_min/mean`, verifier utilisation, batch-size and batch-wall statistics, queue
wait, draft and round components, in-window rounds per client, workload lifecycle (INVALID flag), real/virtual time ratio,
causality ledger violations. Thresholds are fixed **before** seeing data:

| Outcome (N=8 → N=16, all 3 seeds consistent) | Rule | Reading |
|---|---|---|
| **SUPPORTS RQ1** | `Y(16) ≤ 1.10 Y(8)` and `x_min(16) ≤ 0.65 x_min(8)` and `x_min/mean ≥ 0.8` | goodput plateaus while the per-client floor falls (ideal 1/N gives 0.5) |
| **FALSIFIES concealment (in this range)** | plateau and `x_min(16) ≥ 0.90 x_min(8)` | the floor does not fall; aggregate goodput is not hiding anything here |
| INCONCLUSIVE | `Y(16) ≥ 1.5 Y(8)`, or N=8/16 missing or INVALID | capacity not reached or evidence missing; extend N, do not claim |
| PATHOLOGY | `Y(16) < 0.9 Y(8)` | contention/overhead; diagnose before any capacity statement |
| MIXED | anything else | report numbers, do not summarise as support |

Also reported (not rules): the N=1 draft latency vs the profile (validates 22.2 ms/token), the batch-size histogram (does batching
ever exceed 8?), and the between-seed spread of `x_min` per N — **this spread is the input that sizes a later certification**
(power at 10 % spread: K = 5 → 41 %, 7 → 73 %, 12 → 98 % to certify a +1.67σ margin).

**Descriptive vs certified**: everything in the pilot is descriptive (K = 3, no Bonferroni claim, no boundary). The words
"certified", "N\*(x)", "capacity" and "ICA" must not be used for pilot results. A certified boundary point needs
`classify_certified` with K ≥ 5 (typically 8–12), INVALID-free runs, and both neighbours; that is a different, much larger campaign.

## 7. Threats to validity that remain (and how the pilot treats them)

| Threat | Treatment |
|---|---|
| E1 draft-emulator contention | `isolated_profile` (approval needed); if refused, interpret only the verifier-attributable part via the logged components |
| causal mode untested with real GPU concurrency | first run (N=8) is a gate: ledger violations = 0, real/virtual ≤ 3, no exhausted client, ≥ 20 in-window rounds/client (`scripts/c1/pilot_gate.py`) |
| D3 bandwidth/active-client reads | `proportional` allocator, fixed policy, payload ≈ 100 B ⇒ ≤ 0.03 ms/round effect |
| one policy, one population, one γ | RQ1 is a statement about this configuration; no generalisation claimed |
| `x_min/mean` fairness | reported; < 0.8 downgrades a SUPPORTS to MIXED |
| monotonicity in N | not assumed: all six N are run, no search |

## 8. GPU budget (auditable)

Per (N, seed) run: `130 s startup + 160 s × r(N) × c + 20 s teardown`, c = causal-waiting factor on real time (unmeasured; 1–3).
`scripts/c1/rq1_workload_and_cost_budget.py` → `results/c1_20261020/rq1_workload_and_cost_budget.json`.

| Design | c = 1 | c = 2 | c = 3 (hard cap) | Per job (1 seed, 6 N), c=1 / 2 / 3 |
|---|---|---|---|---|
| **Full: N ∈ {1,2,4,8,12,16} × 3 seeds = 18 runs** | **1.57 node-h** | **2.39 node-h** | 3.21 node-h | 31 / 48 / 64 min |
| Reduced: N ∈ {1,4,8,16} × 2 seeds = 8 runs | 0.69 | 1.05 | 1.41 | 21 / 32 / 42 min |

1 node = 8 GCDs (the pilot uses `gpu:8` per job; node-hours × 8 = GCD-hours). Layout: 3 jobs (one per run-seed), each 1 h 15 min
limit, six sequential runs, N=8 first. Job 1 is submitted alone; the others only if its gate passes. Abort criteria: any gate failure,
any INVALID run, projected total > 3.2 node-h. Raw data stays on `/scratch`; only compact per-run summaries and the analysis JSON go
to git. Scripts (not submitted): `scripts/c1/run_rq1_pilot_job.sh`, `scripts/c1/pilot_gate.py`, `scripts/c1/analyze_rq1_pilot.py`.
Order of magnitude of what this does **not** buy: one certified N\*(x) point needs ≈ 12 distinct N × 8 seeds ≈ 96 runs ≈ 8 node-h.
