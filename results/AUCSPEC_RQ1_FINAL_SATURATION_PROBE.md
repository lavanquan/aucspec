# AUCspec RQ1 — final bounded saturation probe (C1.4, exploratory, one seed)

One run-seed, one job, hybrid emulator, fixed-γ policy. No certified N\*(x), no ICA, no statistical significance, no policy comparison. Labels: **[V]** verified from logged data, **[H]** hypothesis, **[inf]** inference from logged quantities.
The N = 24 → N = 32 analysis below is **exploratory, motivated by the C1.3 observations**; it is *not* the pre-registered confirmatory N = 8 → N = 16 test, whose thresholds are untouched.

**Result in one paragraph.** Both N = 28 and N = 32 ran to completion on the `batch_cap_16` serving configuration with no OOM, no causality violation and no workload exhaustion [V]. The verifier is 100 % busy at both, goodput has flattened
(Y = 81.6 → 84.2 → 86.5 for N = 24 → 28 → 32, +3.3 % and +2.7 %) while the per-client floor keeps falling roughly as 1/N (x_min = 3.28 → 2.89 → 2.58, −11.9 % and −11.0 %) [V]. Per-client round time equals the sum of the sequential verifier batches of a cohort to within 1 ms [V].
This is the goodput-plateau-with-falling-floor regime that RQ1 describes, observed descriptively for this policy and population.

## 4. Observations
1. **Plateau [V].** Y: 56.4 (16), 81.6 (24), 84.2 (28), 86.5 (32). The last two steps are +3.3 % and +2.7 %; N·x_min = 78.8 → 81.0 → 82.4. Y(32)/Y(24) = 1.060.
2. **The floor keeps falling [V].** x_min(32)/x_min(24) = 0.784 against 0.750 for pure 1/N scaling (24/32); each step is −12 %/−11 %. The floor falls while goodput is approximately flat (≤ 3.3 % per step), i.e. aggregate goodput no longer reflects the per-client loss.
3. **Round time = the verifier cycle [V].** Per-cohort sum of batch walls (mean per batch size, window): N = 24: 275 + 529 = 804 ms vs round 812; N = 28: 402 + 517 = 919 vs 920; N = 32: 2 × 511 = 1022 vs 1023. The verifier is 100 % busy for N ≥ 28 (corrected occupancy 1.000), 260/261 and 234/235 batches start the instant the previous one ends.
4. **Sequential batch cycles / lockstep [V].** Lockstep full-N batching is gone for N > 16: N = 24 → 8 + 16, N = 28 → 12 + 16, N = 32 → 16 + 16. A 16-request batch costs 535 / 529 / 517 / 511 ms at N = 16 / 24 / 28 / 32 — **no inflation with N**.
5. **Queue delay and fairness [V].** Mean queue wait rises 144 → 263 → 347 → 408 ms (the 150 ms wait floor is included); at N = 32 all clients wait alike (396–420 ms) and `x_min/mean` is 0.953 (0.962 at 28, 0.966 at 24). Fairness of the rate floor decreases slightly with N but stays high.
6. **Batch-wall and token dependence [V].** Wall time grows with processed tokens at 0.20 ms/token in every run (slopes 0.203, 0.189, 0.199, 0.196; r = 0.65–0.92); the largest batch has 3,451 tokens. Slow batches (> 2× median): 5 of 342 at N = 28 (1 in warm-up), 1 of 312 at N = 32, no bursts (lag-1 autocorrelation ≈ 0); no first-run effect is visible (N = 28 was the first run of this job).
7. **GPU memory [V].** Device 0 (63.98 GiB): after engine init 42.8 GiB allocated / 43.0 reserved; run peaks **55.98 GiB allocated, 63.40 GiB reserved at N = 28** and **55.72 / 63.45 GiB at N = 32** — the transient logprob workspace adds ≈ 13 GiB and the allocator reaches ≈ 99 % of the device. **Headroom at cap 16 is thin (≈ 0.5 GiB of reserved memory)** although no OOM occurred; the cap-32 N = 24 failure is consistent with this budget [H].
8. **Prefill scheduling [inf].** With `max_num_batched_tokens = 4096` and chunked prefill off, no batch of any run (largest 3,451 tokens; 0 batches above 4,096) should have needed more than one scheduler step; engine step counts were not logged, so this is an inference from token counts.
9. **Real/virtual cost [V].** 1.67, 2.15, 3.07, 3.21, 3.28 (N = 8 … 32): roughly flat above N = 24. Run wall times 268–526 s per 160 virtual s.

## 5. Interpretation: batching or emulator artifact? (question C)
The trend is **dominated by verifier batching [V + inf]**: the virtual round equals the sum of sequential measured batch walls to within 1 ms; the 16-request batch wall does not grow with N (535 → 511 ms), so emulator load (single-process draft contention, real/virtual 3.2×) is **not** inflating the measured verifier time; the draft part of the round is a constant 44 ms by the isolated profile (plus 50 ms RTT and a 150 ms batch wait). Residual emulator influence cannot be excluded: the verifier shares a process/node with the draft threads, the population is homogeneous (lockstep cohorts, ties broken by client id so some clients are always in the first batch), and the batch wall is a physical measurement on a single GCD.

## 6. Answers
* **A. Descriptive evidence of a goodput plateau?** Yes, descriptively and for one seed: Y gains 3.3 % and 2.7 % over N = 24 → 28 → 32 with the verifier 100 % busy, after +44 % from 16 to 24.
* **B. Does x_min fall while goodput is ~flat?** Yes: x_min falls 11.9 % and 11.0 % per step (0.784 over 24 → 32 vs 0.750 for 1/N).
* **C. Verifier batching or emulator artifact?** Mainly verifier batching (section 5), with the stated caveats.
* **D. What would rigorous certification need?** A certified boundary point (e.g. x = 3.0, which this policy crosses between N = 24 (3.28) and N = 28 (2.89)) requires the Student-t classifier with K ≥ 5 (typically 8–12) independent run-seeds at each probed N, ≈ 6 distinct N (24…29 plus local re-certification and falsification probes) ⇒ ≈ 50–70 runs. A run at N ≈ 26 costs ≈ 11–13 min (≈ 0.2 node-h incl. ~2 min startup, real/virtual ≈ 3.2), so **≈ 10–14 node-h per x-value**, about 40–55 node-h for a four-point frontier, plus a decision on the cost gate and memory headroom. The current budget has 1.474 node-h left, which pays for **≈ 2 additional seeds of N ∈ {8, 16, 24, 32}** (≈ 0.65 node-h per seed from the measured run times) to test that the curve above replicates — not for certification.
* **E. Stop extending RQ1 and switch to the controller-mechanism research?** **Yes.** The RQ1 phenomenon is established descriptively for a fixed policy: a verifier-bound regime where goodput saturates (≈ 84–86 tok/s) while the per-client floor falls ≈ 1/N and the saturation point lies near N ≈ 24–28 on this hardware. Further RQ1 work (replication, certification) is a measurement-cost question that is better spent once a capacity-aware controller exists to compare against the fixed policy in this regime. If the paper needs the descriptive curve replicated before submission, the affordable minimum is the two extra seeds above (≈ 1.3 node-h), to be decided later.
